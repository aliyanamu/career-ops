# Career Direction

Living log of *where the career is going* and the real-life requirements behind it — the "why" that steers the whole pipeline. Each file here is one direction (a pivot, a market, a bet). One is marked **ACTIVE**; the agent reads the active direction and lets it bias scanning and scoring **without ever relaxing hard requirements**.

This is user-layer context (like `modes/_profile.md`). Updates never overwrite it.

## Active direction

**→ [japan-pivot.md](japan-pivot.md)** — pivot toward Japan-based / Japan-company software roles, English-first (Door A), Japanese learned in parallel.

## How a direction steers the pipeline

A direction file can set a **location/market bias**. That bias is a *ranking nudge*, layered on top of — never replacing — the hard requirements in `modes/_profile.md`:

- **Hard requirements gate first** (e.g. remote-only, no US-region-locked, no Israel). A role that fails these is out regardless of direction.
- **Then the active direction re-weights what survives.** For the Japan pivot: among roles that already pass the hard gate, push **Japan-located or Japan-company** openings up the ranking. A remote-from-Indonesia role at a Tokyo company outranks an otherwise-equal role with no Japan tie.
- **Where to scan** follows the same bias: `portals.yml` already front-loads Japan English-first boards (TokyoDev, Japan Dev, gittap) and companies (Mercari, Rakuten, PayPay, LINE, Woven/Toyota), with remote-global web3 as the differentiator.

So: *hard requirements = the filter, active direction = the sort.*

## Adding / switching direction

1. Add a `{name}.md` here (copy the shape of `japan-pivot.md`: decision, requirements, plan, checkpoints).
2. Point **Active direction** above at it.
3. If it changes *where* to scan, update `portals.yml`. If it changes *how* to score, update `modes/_profile.md` (Location & Comp Policy).
